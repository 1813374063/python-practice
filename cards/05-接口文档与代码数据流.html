第 2 阶段 · 接口基础

接口文档与代码数据流

一条工单如何从输入走向模型，再变成可校验的评估结果

1本卡目标

  • 能把官方接口文档拆成“请求字段”和“响应字段”。
  • 能看懂 required、nullable、Default value 等标记。
  • 能把接口字段与 prompt_eval.py 的具体代码位置对应起来。
  • 能追踪一条工单从输入、组装、调用、解析、校验到汇总的完整数据流。

2最重要的总结构

请求 Request
→ 程序告诉模型：使用什么规则、处理什么任务、返回什么格式

响应 Response
→ 模型告诉程序：回答正文、结束原因、token 用量
阶段代表字段一句话
请求model选择哪个模型
请求messages发送规则、历史、示例和当前任务
请求response_format选择文本或 JSON 输出
请求max_tokens限制生成 token 总量
响应choices[0].message.content读取可见正文
响应choices[0].finish_reason判断为什么停止生成
响应usage查看 token 工作量

3官方文档的字段标记

标记含义
string、number、object、array字段的数据类型
required调用接口时必须提供
nullable可选，不传时使用默认行为
Default value不传时的默认值
Possible values允许的取值或范围
示例：model string required 表示字段名为 model，类型是字符串，而且必须传值。

4请求字段

4.1 model

model = "deepseek-flash"

指定由哪个模型处理请求。可选模型会变化，以官方文档和当前账号为准。

4.2 messages

messages = [
    {"role": "system", "content": "分类规则和 JSON 格式"},
    {"role": "user", "content": "示例工单"},
    {"role": "assistant", "content": "标准答案"},
    {"role": "user", "content": "当前新工单"},
]
角色作用
system任务、规则、限制、输出格式
user用户输入或 Few-shot 示例输入
assistant模型历史回答或 Few-shot 标准答案
DeepSeek 多轮对话文档说明接口是 stateless，服务器不会记录请求上下文。需要的历史必须由程序每次重新发送。

4.3 response_format

response_format={"type": "json_object"}

开启 JSON Output 后，接口保证生成内容是合法 JSON，但不会保证业务字段完整，也不会保证分类一定正确。提示词还要说明字段和结构，程序还要继续校验。

4.4 max_tokens

max_tokens=4000

限制本次生成 token 总量。它不只包括最终正文，也可能包括推理 token。额度不足时会出现 finish_reason="length"，正文可能不完整或为空。

4.5 temperature 与 thinking

字段结论
temperature范围 0 到 2，默认 1，值越低通常越集中
temperature 与 thinking官方文档说明 thinking mode 下 temperature 没有效果
thinking控制是否进入思考模式，当前文档默认 enabled
reasoning_effortnone、low、high、max，默认 high

5响应字段

content = response.choices[0].message.content
finish_reason = response.choices[0].finish_reason
usage = response.usage
字段含义
choices候选回答列表
choices[0]第一个候选回答
message.content可见正文
finish_reason=stop正常结束
finish_reason=length达到生成或上下文长度上限

usage 的公式与边界

total_tokens = prompt_tokens + completion_tokens
completion_tokens 不只包含最终可见正文，还可能包含推理 token。因此可能出现 completion_tokens 很大，但 content 很短或为空。

6prompt_eval.py 六阶段数据流

阶段代码位置输入到输出
01 输入工单第 176 行TEST_CASES → case 字典
02 组装请求build_messages() 第 118 到 137 行规则、示例、新工单 → messages 列表
03 调用模型call_model() 第 142 到 147 行请求字段 → response 对象
04 解析响应第 149 到 153 行JSON 字符串 → Python 字典
05 校验结果validate_result() 第 160 到 171 行检查字段、类别和优先级
06 汇总存档第 185 到 246 行实际值与预期值 → 准确率和 JSON 文件

8真实踩坑与结论

现象原因处理
模型返回空字符串1200 个 token 被推理过程耗尽，finish_reason 为 length提高 max_tokens，并加入有限重试
JSON 解析失败模型没有返回合法 JSON捕获 JSONDecodeError，使用 raise ... from 保留原因
字段缺失JSON 语法合法，但业务结构不完整使用集合差集检查必要字段
8/8 准确率测试集小，且部分样例与 Few-shot 示例重合不能外推为真实生产准确率
当前目标的最终标准不是背下代码，而是能回答：输入在哪里、请求在哪里组装、模型在哪里调用、响应在哪里解析、结果在哪里校验和保存。
